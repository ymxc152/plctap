# Case 03: 合法 RTU 帧被按 Modbus TCP 硬解 —— 诊断引擎为什么需要双轨判别

> 时间锚点: v0.2/M2 诊断引擎设计期 (HANDOFF §5.7 关键坑 ③) → v0.5.1 modbus_rtu 端点复用同一轨道
> 相关代码: `src/plctap/diag/engine.py` (_collect_frame 双轨三档判别 / _RTU_GATE), `src/plctap/protocols/modbus/codec.py` (parse_rtu / validate_rtu)
> 帧样例: 全部取自 `eval/corpus/modbus_m2.yaml` 合成语料 (红线 1)

## 背景/现象

Modbus 在 TCP 上有两种帧壳: MBAP 封装 (事务号 2B + 协议标识 2B + 长度 2B + unit + PDU) 与 RTU 裸帧 (从站地址 + PDU + CRC16, 多项式 0xA001 小端)。诊断引擎的入口是统一的: 现场抓到的帧、从日志里抠出来的 hex 串, 都可能属于任何一种 —— 但入口拿到的是一串裸字节, 没有"这是 TCP 还是 RTU"的标签。

现象是设计期评测语料直接暴露的: 语料里有一条 `rtu_ok`, 输入合法 RTU 读响应帧 `010300000001840a` (CRC 自洽), 期望**零候选**。初版引擎按 TCP 轨硬解, 产出两条互相打架的伪候选:

- 前 6 字节被当 MBAP: 事务号 0x0103、协议标识恰好 0x0000 (蒙混过关)、长度字段 0x0001 与实际字节数不符 → "**MBAP 长度不符, 疑似粘包/半包**";
- 尾两字节 `840a` 被当 RTU CRC 重算 → "**RTU 帧校验和错**"。

一条完全健康的帧, 得到两个错误的结论。反过来, 12 字节 TCP 帧喂进 RTU 轨, 尾字节同样会被当 CRC 算出"校验和错"噪声。

同一串字节 `01 03 00 00 00 01 84 0a` 的双轨对照:

| 解读 | 字段拆解 | 结果 |
|---|---|---|
| RTU 轨 (正确) | addr=01, fc=03 (读保持寄存器), start=0000, qty=0001, CRC=0x0A84 (小端, 与计算一致) | 完整自洽, 零候选 |
| TCP 硬解 (错误) | tid=0x0103, proto_id=0x0000 (恰好蒙混), length=0x0001 (其后实有 2 字节, 不符), unit=0x84, fc=0x0A (不在已知功能码范围) | 伪候选: "MBAP 长度不符" 等 |
| TCP 硬解 + RTU 噪声 (更糟) | 尾字节 84 0a 再被当 CRC 重算 | 伪候选: "RTU 校验和错" |

注意"形似 MBAP"的迷惑性: proto_id=0 这一最显眼的判别项恰好通过 —— 单看任何一项校验都像 TCP, 只有"整帧能否完整自洽解释"才能定轨。

## 探测与证据

证据就在解析结果的字段层: 合法 RTU 帧按 TCP 硬解后, `protocol_id=0` 恰好通过、而 `length_field_consistent` 失败 —— "形似 MBAP"是**部分字段巧合**, 不是结构成立。判别器需要回答的问题因此不是"像不像 TCP", 而是"**哪条轨道能把整帧解释完**"。这决定了判别不能靠单一校验项的通过率投票, 而要按"能否完整自洽解释"分档。

## 定位

诊断引擎的核心风险不是漏报, 是**伪候选挤掉真结论** (top1 排序被噪声占据)。所以设计成三档判别, 每档决定校验清单与事实来源:

1. **TCP 结构合法 → 单轨 TCP**。合法 TCP 帧的尾字节不是 RTU CRC, 不跑 RTU 轨, 直接按 MBAP 校验清单出事实。
2. **TCP 硬解失败但 `parse_rtu` 完整可解释 → 单轨 RTU**。合法 RTU 帧不该产出"MBAP 长度不符"这类按 TCP 硬解的伪结论 —— 此档把 rtu_ok 从两条伪候选修回零候选。
3. **双败 → 双轨合并, 但 RTU 侧过门控**。只有帧"形似 RTU" (功能码已知, 且异常/请求/响应 payload 形状自洽, 见 `validate_rtu` 的 `_RTU_GATE`) 才把 RTU 侧校验失败项并入, 否则 12 字节 TCP 帧的尾字节会被当 CRC 算出噪声、压过真正的 TCP 结论。

决策速查:

| 档位 | 触发条件 | RTU 轨参与? | 典型输入 |
|---|---|---|---|
| 单轨 TCP | parse_auto 判 MBAP 结构合法 | 否 (合法 TCP 尾字节不是 CRC) | `0001 0000 0006 01 03 ...` |
| 单轨 RTU | TCP 硬解失败 且 parse_rtu 完整 valid | 是, 唯一事实来源 | `010300000001840a` |
| 双轨合并 | 两轨都解释不通 | 仅过 `_RTU_GATE` (功能码已知 + payload 形状自洽) 才并入 | 畸形/截断帧 |

另一条配套纪律: 配对交叉校验 (tid 串包检测) 只对 TCP 轨启用 —— RTU 帧没有事务号, 请求-响应配对规则不同, 不能共用。

## 结论与修复

三档判别随 M2 引擎一次落进 `engine.py`, 此后成为 Modbus 轨道的地基:

- 评测从 Modbus 三档 18/18 (v0.2) 扩到五档 35/35、八档 49/49; 批量日志档专门有一条 `log_multi_issue_mix`: 连接拒绝噪声文本 + TCP tid 串包 + RTU 坏 CRC 帧三问题混排, 考"提取-配对-双轨判别"的聚合能力。
- v0.5.1 modbus_rtu 端点 (串口服务器/网关 RTU 透传模式) 与 modbus **帧级同轨**: 判别、知识库、写语义共用, 新端点零新增判别逻辑。
- detect 的 modbus_rtu 指纹与判别同源: "RTU 帧 CRC 自洽且功能码回显 (无 MBAP) —— 网关/串口服务器 RTU 模式"。
- 与双轨判别配套的确定性边界: 引擎只输出结构化候选 (规则引擎 + kb.yaml), 不生成自然语言 —— 候选才能被门控、被排序、被抑制, 这正是本案例的解法能"做进代码"的前提。

## 复盘

- "解析失败的方式"是诊断证据, 但**只有放在正确的轨道上才是证据** —— 同一个失败项, 在错误轨道上是噪声, 在正确轨道上才是故障本体。
- 诊断类工具的排序即结论: 用户/Agent 只看 top1, 伪候选不是"多了一条无用信息", 而是把真结论挤出了注意力。
- 先写期望 (rtu_ok 零候选) 再写实现, 让设计缺陷在语料层显形 —— 评测语料不只是回归网, 也是设计工具。
- 混排场景 (TCP 帧 + RTU 帧 + 自由文本同现) 是真实现场日志的常态, 单帧思维覆盖不了, 语料要按混排设计。

## 如何用 plctap 复现/验证

三档各取一条语料合成帧, 观察判别结果与候选差异:

```text
diagnose(protocol="modbus", frame_hex="010300000001840a")            # 合法 RTU: 零候选 (单轨 RTU)
diagnose(protocol="modbus", frame_hex="01030000000184f5")            # CRC 坏: RTU 轨校验和错候选
diagnose(protocol="modbus", frame_hex="0003000000100103020000")      # TCP 长度字段不符: 单轨 TCP, 无 RTU 噪声
diagnose(protocol="modbus", frame_hex="000100000003018302")          # TCP 异常响应: 非法数据地址候选
```

混排日志聚合 (三问题并存: tid 串包 + RTU 坏 CRC):

```text
diagnose(protocol="modbus", log_snippet="TX 000100000006010300000002 | RX 00420000000701030400010002 | TX 01030000000184f5")
```

单帧结构对照 (看"形似 MBAP"的字段级证据):

```text
parse_frame(protocol="modbus", frame_hex="010300000001840a")         # auto 判轨道后结构化解析
validate_frame(protocol="modbus", frame_hex="010300000001840a", direction="resp")
```
