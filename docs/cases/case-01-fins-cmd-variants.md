# Case 01: FINS/TCP 数据帧命令字 0x04 vs 0x02 —— "主流"是测出来的, 不是读出来的

> 时间锚点: v0.2 期 (M2 实装) → 2026-09-06 全量交叉验证修复 (提交 84dad0a, HANDOFF §5.12)
> 相关代码: `src/plctap/protocols/fins/codec.py` (FINS_EXCHANGE_COMMANDS), 提交记录见 git log
> 帧样例: 全部为本仓库 codec 构造的合成帧 (红线 1), 台架地址 127.0.0.1

## 背景/现象

FINS/TCP 是两层协议: 外层 TCP 头 16 字节 (`"FINS"` 魔数 4B + 长度 4B 大端 + 命令 4B 大端 + error 4B 大端), 内层 FINS 头 10 字节 (ICF/RSV/GCT + 网络地址 5B + SID) + 命令码 (0101 存储区读等), 全大端。TCP 层命令 0x00/0x01 是节点连接请求/确认, 而**承载 FINS 数据帧的命令字**存在 0x02 与 0x04 两个值。

初版实现把数据帧命令定为 0x04: 依据是一份手册记述加单一开源参考实现, 两相印证, 自洽。更隐蔽的是, 当时把 0x02 保留为"连接拒绝"语义 (旧常量名 `TCP_CMD_CONNECT_REFUSED`), 整个心智模型闭环了 —— **单实现对照下的每一条证据都指向 0x04, 没有任何反例**。

现象出现在四权威实现台架 (pymodbus / python-snap7 / IoTClient / 自建 MC fixture, 各起 127.0.0.1 高位端口) 的全量交叉验证: plctap 对 IoTClient OmronFinsServer (127.0.0.1:9600) 探测通 (0x00/0x01 握手正常)、读必挂; 反向把 IoTClient 客户端打进 plctap 钓鱼监听, 也收不到响应。互通面两端同时出问题, 说明不是对端实现的孤例 bug。

差异帧的字段级对照 (合成帧, TCP 头 16B + FINS 头 10B, 全大端):

| 偏移 | 字段 | 0x04 变体帧 (初版实现) | 0x02 主流帧 (生态一致) |
|---|---|---|---|
| 0-3 | magic | `46 49 4e 53` ("FINS") | 同左 |
| 4-7 | length (BE) | `00 00 00 16` (=22) | 同左 |
| 8-11 | **command (BE)** | `00 00 00 04` (变体) | `00 00 00 02` (主流) |
| 12-15 | error (BE) | `00 00 00 00` | 同左 |
| 16+ | FINS 层 | ICF=c0(响应) ... SID, 命令码 0101, 端结码 1101 (地址范围错误) | 同左 |

除命令字外逐字节同构 —— 语义完全相同, 互通性却一个通一个断。

## 探测与证据

1. **切变量**: 同一台架、同一地址、同一读语义, 只换客户端库 —— pypi `fins` 库客户端与 IoTClient 模拟器互通正常。排除模拟器问题, 锁定我方请求帧。
2. **抓帧逐字节对比**: 同语义的存储区读请求, 我方与生态实现的唯一结构差异是 TCP 头偏移 8-11 的命令字段: 我方 `0x00000004`, 生态 `0x00000002`。
3. **第二、第三实现交叉**: 读 node-omron-fins (JS 生态) 源码, 数据帧同为 0x02。三个互相独立的实现 (C#/Node/Python) 一致, 且 IoTClient 模拟器经真机验证。
4. **定性 0x04**: 手册对 FINS 帧交换命令的记述存在版本/解读分歧, 0x04 是部分手册与实现记录的变体值 —— 不是谁"错"了, 是规范留了变体空间, 而生态收敛在 0x02。

## 定位

失败模式归类: **用单一来源的"应该是什么"替代了生态实测的"实际是什么"**。协议规范 (尤其是描述有版本分歧的字段) 不能当作唯一判据; 判据等级应当是: 单一手册 < 单一开源实现 < 多实现一致 + 真机互通。同时, 探测通了 (握手层 0x00/0x01 正确) 而数据层挂, 恰好说明分层验证能把故障切到具体一层 —— 这也是 probe 与 read 分层设计的价值。

## 结论与修复

提交 84dad0a (2026-09-06), 策略是"**解析宽容、发送保守**":

- `FINS_EXCHANGE_COMMANDS = frozenset({0x02, 0x04})`: parse_request / parse_response / 诊断 / 监听对两个命令值**等价接受** —— 现场设备两派都有, 解析器没资格替用户站队。
- adapter 发送一律用 0x02: 与真实设备及主流客户端的互通面最大。
- 监听器响应**回显请求的命令值** (来 0x02 回 0x02, 来 0x04 回 0x04), 修复 IoTClient 客户端打入钓鱼监听无响应的互操作缺陷 —— 回显而不是假设, 是监听/代理类工具的基本纪律。
- 连接拒绝语义归位: 拒绝以连接确认帧的 error 字段承载 (如节点冲突), 短 payload 的 0x02 帧在 auto 方向判别中仍按拒绝处理, 与生态行为一致。

配套: 评测语料 fins 档的帧样例随后在 b319374 (v0.2.0) 同步更新, 判分语义不变 (eval/README.md 语料纪律条款的执行样例)。

## 复盘

- "主流"不是从一份文档推出来的, 是从生态测出来的。三实现一致 + 真机互通之前, 任何"规范答案"都只是假设。
- 判据等级要显式化, 当时缺的正是这张表:

  | 等级 | 证据 | 当时状态 |
  |---|---|---|
  | L1 | 单一手册记述 | 有 (采信了 0x04) |
  | L2 | 单一开源实现 | 有 (强化了 0x04) |
  | L3 | 多个独立实现一致 | 缺 —— 补齐后立刻翻案 |
  | L4 | L3 + 真机互通 | 定案标准, 此后按此执行 |

- 解析器要宽容 (等价接受变体), 发送端要保守 (跟随最大互通面) —— 两个方向的纪律不能混用。
- 抓串包、跨网关、冷门协议场景里, "与主流实现逐字节对帧"是最快也最不可否认的证据形态; 本次定位全程只花在"换客户端 + 对帧"上, 没有走弯路。
- 这也是 diagnose 把 `parse_frame` 的逐字段证据 (带 byte_offset 与 raw_hex) 作为输入的原因: 结论要能落到具体字节。

## 如何用 plctap 复现/验证

下面两帧是同构合成帧 (仅 TCP 命令字不同): 0x04 变体帧取自评测语料, 0x02 是生态主流孪生帧。两者都应解析为 valid, 且 FINS 层端结码 0x1101 (地址范围错误) 一致 —— 演示"解析侧等价接受":

```text
parse_frame(protocol="fins", frame_hex="46494e53000000160000000400000000c000020000000002000101011101")
parse_frame(protocol="fins", frame_hex="46494e53000000160000000200000000c000020000000002000101011101")
```

对同一帧跑诊断, 应命中端结码 1101 (存储区边界/地址范围) 候选, 证明变体帧照常进入规则引擎:

```text
diagnose(protocol="fins", frame_hex="46494e53000000160000000400000000c000020000000002000101011101")
```

观察监听器的命令值回显 (设备只能当 client 时):

```text
start_listener(protocol="fins", mode="respond_normal", port=0)   # 记下返回的实际端口
# 让对端分别以 0x02 / 0x04 帧打入, 然后:
get_listener_frames(port=<实际端口>)
stop_listener(port=<实际端口>)
```
