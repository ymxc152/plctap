# Case 05: S7 write 漏调 on_frame —— 测试全绿不等于安全闭环

> 时间锚点: v0.5.5 修复 (2026-09-07, 提交 5e86d92, HANDOFF §5.18/§5.19) — 本项目唯一一次安全红线级线上缺陷
> 相关代码: `src/plctap/protocols/s7/adapter.py` (write), `tests/test_smoke.py` (test_audit_log_written_on_s7_write), `docs/ADD_PROTOCOL.md` (防复发条款)
> 地址: 127.0.0.1 台架; 审计日志路径 ~/.plctap/audit.jsonl

## 背景/现象

plctap 的安全模型有两道独立防线: **闸门** (PLCTAP_ALLOW_WRITE=false 时写类工具根本不注册) 与**审计** (闸门开启后, 所有写/发送动作逐帧写入 JSONL 审计日志, 不可关, **发送前留痕、失败也留**)。后者对应架构红线 D5: 审计的用途是事后追溯 —— 连"尝试了但连接失败"的写都必须有据可查。

| 防线 | 回答的问题 | 本案例中的状态 |
|---|---|---|
| 闸门 (注册可见性) | Agent 能不能发起写? | 正常 (显式开启才注册) |
| 审计 (逐帧留痕) | 写了什么、何时、发给谁? | **对 s7 完全失效** —— 钩子从未被调用 |

时间线: 写审计回归自 P2 期 (2026-09-04) 就有, 但只测 modbus → v0.2.0 (2026-09-05) 新增 s7 端点, 审计路径未单独验证 → 此后三轮发布全量测试持续全绿 → v0.5.5 (2026-09-07) 发布 wheel 台架验收抓出。

现象出现在发布 wheel 的台架验收: 按固化方法学走四步 (① 起仿真器台架 modbus/s7/melsec/fins 各据 127.0.0.1 高位端口 → ② `uv run --no-project --with plctap==X.Y.Z` 用 PyPI wheel 经 fastmcp Client 走完整 MCP 工具链 → ③ 第三方权威客户端独立读回 → ④ **审计逐帧计数**), 逐协议写入全部成功、python-snap7 交叉读回一致, 但第 ④ 步核对审计日志时: modbus / fins / melsec 的写各有留痕, **s7 的写帧计数为 0**。写操作真实发生了, 审计里却没有它。

## 探测与证据

1. **审计逐帧计数直接定位缺口**: 台架脚本对每类写操作计审计条数, s7 一项缺计 —— 不是日志丢了、格式坏了, 是该协议的审计路径从未被触发。
2. **代码走查**: `S7Adapter.write()` 在 `build_write_request(...)` 构建请求帧后直接进入网络动作, 方法签名没有 `on_frame` 参数、也没有调用它; 对照 modbus/fins/melsec 适配器, 三者都在帧构建后、发送前调用 `on_frame(request.hex())`。
3. **为什么 520 项单测全绿却漏网**: 写审计的回归测试从 P2 期就只有 modbus 一条 (`test_audit_log_written_on_write_call`); s7 端点是 v0.2.0 新增的, 此后每轮全量测试验证的都是"已有协议的已知路径", **没有任何一条测试断言过"每个实现了写的新协议都必须留审计痕"**。
4. **危害定性**: 审计被静默短路, 意味着安全模型的第二道防线对 s7 完全失效 —— 且发送前不留痕连"写失败"都无据可查, 恰是追责场景里最需要的记录。红线级, 无争议。

## 定位

根因是**流程性的, 不是技术性的**: 写能力是"适配器各自实现、基类不强制"的模式, `on_frame` 挂钩就成了每个新适配器的自觉义务; modbus 时代把义务做对了, 但没有把"做对了"固化成**可检查的契约**。技术教训只有一个: 安全属性 (审计、闸门) 不能假设"基类统一兜底"或"后来者会照抄先行者", 必须逐协议显式验证。

由此固化到新协议接入流程的逐项检查 (写能力相关):

| # | 检查项 | 验证手段 |
|---|---|---|
| 1 | 闸门关闭时写工具不可见 | list_tools 断言 (冒烟测试) |
| 2 | write() 声明 on_frame 且在帧构建后、网络动作前调用 | 代码走查 + 台架审计计数 |
| 3 | 写连接失败也留痕 | 对不可达端口发起写, 断言审计已有记录 |
| 4 | 写能力元数据不虚报 (真覆写才算 write:true) | 类级方法身份比较 (server 层) |

## 结论与修复

提交 5e86d92 (2026-09-07, v0.5.5), 修复 + 回归 + 防复发三层:

1. **修复**: `write()` 签名补 `*, on_frame=None`; 请求帧构建后、**任何网络动作前**调用 `on_frame(request.hex())` —— 与 modbus/fins/melsec 语义逐字对齐。"任何网络动作前"是语义关键: 连接失败的写同样已经构成了"尝试写"这个事实。
2. **回归**: 新增 `test_audit_log_written_on_s7_write` —— 对 127.0.0.1:1 (注定无从站) 发起 s7 写, 断言握手必然失败, **且审计日志里已出现完整帧记录** (`"tool": "plc_write"`, target 形如 `s7://127.0.0.1:1`)。用例名即规范: 写连接失败也必须留痕。
3. **防复发条款**: docs/ADD_PROTOCOL.md Step 3 落成硬性文字: "write() 必须声明 on_frame 参数并在请求帧构建后、任何网络动作前调用 on_frame(request.hex()) —— 漏调意味着该协议的写操作完全绕过审计 (s7 曾踩此坑, v0.5.5 修复)"。新协议接入必读文档从此带此坑记录。
4. **方法学归位**: 该缺陷由"发布 wheel 台架验收 (审计逐帧核对)"抓出, 此方法在 v0.5.5 起固化为每次发布的标准验收项 (HANDOFF §5.19, 台架验收 21/21)。


## 复盘

- **测试全绿 ≠ 安全闭环**: 单测覆盖"被想到的路径", 而安全缺陷恰恰藏在"没人想到要测的路径"。功能测试与安全验收是两个正交的检查面, 后者需要独立的方法学 (发布态 wheel + 真实工具链 + 逐帧计数) 而不是更多单测。
- 这类缺陷的探测成本极低 (对账一次计数), 但发现窗口极窄 (只在发布验收的真实链路上出现) —— 值得为它保留一道"看起来重复"的人工/脚本对账工序。
- 新协议 checklist 的正确形态: 每条安全红线 (闸门不可见性 / 审计留痕 / 失败也留痕) **逐协议**打勾, 而不是"测过一次全绿"一笔带过。
- 复盘要点: 不是"写了个 bug", 而是"现有测试结构为什么**必然**漏掉它, 以及用什么机制保证下一个协议不再漏" —— 后者才是工程判断力的部分。

```text

plc_write(protocol="s7", host="127.0.0.1", port=1, address=20, value=1, options={"area": "DB", "db_number": 1})
# 调用必然超时/拒绝, 但审计日志 (~/.plctap/audit.jsonl) 应已含一条:
# {"ts": "...", "tool": "plc_write", "target": "s7://127.0.0.1:1 ...", "frame_hex": "...", "caller": "mcp"}
```
